# 理解验证模型选项一致性修复（2026-11-06）

根因：理解验证的 Gateway 配置门禁及运行请求均明确要求 STRICT_JSON_SCHEMA。恢复后的前端却只按“文本生成”能力列出模型，导致 JSON_MODE 的 MiniMax、智谱也能被选择，保存后才被拒绝。

修复：

- 服务端响应增加按用途划分的模型候选，直接复用保存时的 validateRouteManifestSelection，不另造兼容性判定。
- 旧响应的前端回退列表同样过滤理解验证的严格结构化能力。
- 不兼容服务商仍可辨认，但标注“暂无兼容模型”；型号列表为空，保存按钮禁用，说明当前执行要求。
- 普通书籍理解仍保留 MiniMax-M3。自定义文本型号不能冒充理解验证兼容型号。
- 编辑表单会清理该用途上一次的保存反馈，避免旧错误一直显示。

验证：网页 TypeScript、相关 ESLint 通过；3 个定向测试文件 30/30 通过。PostgreSQL 仅使用独立测试库的新建记录：不兼容 MiniMax 保存仍被拒绝且无写入，符合严格要求的测试模型真实写入路由成功。浏览器插件不可用，使用真实组件 Playwright 隔离验收：MiniMax 显示兼容提示且不能提交；切换到声明严格结构化能力的服务商，只显示兼容型号，选择后能够提交并展示成功；书籍理解中的 MiniMax-M3 选项保留。浏览器接口为模拟，不代表真实模型调用成功。

边界：未更改模型能力声明；未删除严格结构化要求；未放宽复述评估的准则、结构、来源证据或 Gateway 回执消费校验；未调用真实模型，未修改用户已保存的路由或历史记录。

因此这是选项和提示修复：MiniMax 与当前目录中仅声明 JSON_MODE 的智谱模型，仍不能用于现有理解验证实现。模型可用于书籍理解，不等于适用于全部功能。
